# Homelab monitoring and operations

Use Horus as the operational source of truth for the homelab. Do not infer current host or service state from memory, old chat output, or a dashboard page alone.

## Always-on rules

- For Tiberius's homelab, establish context in this order: read the shared wiki policy/index and relevant canonical pages, load `proxmox-status` and its state/issues, reconcile the live Proxmox/host layer, then query Horus before reporting current health or choosing an operation target. For a narrow alarm triage already scoped to Horus, query Horus after confirming the target context.
- Use Telegram for operational communication and present decisions with inline action buttons whenever the connected surface supports them. Never claim a notification or button was delivered when it was not.
- For active Horus alarms, carry stable sanitized alarm context into the shared Telegram delivery path and expose separate `🔕 Silenciar` and `⚙️ Threshold` controls only when the target supports them. Authorize both user and chat, keep callback data to a short validated ID/action, keep feedback separate from remediation, apply mute at the documented entity scope, validate threshold choices against the live rule/entity/health target, and read back every write. Attach controls only to the final chunk and treat gateway reload as a separate availability change requiring explicit approval.
- Format operational Telegram messages as a compact executive panel: start with one macro line/block per domain, use a distinct thematic icon for Proxmox (`🖥️`), TrueNAS (`💾`), Docker (`🐳`), Kubernetes (`☸️`), and Uptime Kuma (`📈`), and reserve colored severity icons for the severity itself. For the direct Telegram delivery path, send `parse_mode=HTML` and convert `**bold**`/`` `code` `` markers to `<b>`/`<code>` before sending; never leave Markdown markers in an HTML payload and never wrap the whole body in `<pre>`, because that makes emphasis render literally or not at all. Enforce the Telegram limit after final HTML rendering using UTF-16 code units: keep every message at or below 4,096 units, split long reports at semantic line boundaries with a conservative body budget, and attach feedback controls only to the final chunk. Use short blocks separated by blank lines; do not enumerate healthy containers, pods, datasets, or monitors.
- For this user's homelab, separate detection from notification: keep high-frequency read-only watchdog checks silent while the stable condition set is unchanged, and send full routine status only three times per day—morning, afternoon, and night. Treat changing measurements and counters as report details, not a new incident, unless the condition identity or severity changes.
- Render event-driven operational alerts as deltas, never as full status reports: persist a sanitized prior condition set, compare stable resource/condition identities and severity, and emit only `🆕 novo`, `🔄 alterado`, or `✅ resolvido` entries since the last delivered state. Do not append the Proxmox/TrueNAS/Docker/Kubernetes/Uptime Kuma macro view, healthy inventory, or unchanged measurements to a delta alert; reuse the macro formatter only for scheduled periodic status.
- Debounce transient conditions before notifying: with the five-minute watchdog, require two consecutive observations (10 minutes) for new non-critical service/material conditions. If a condition disappears before confirmation, discard it silently. Critical active alarms may notify immediately. When an announced condition recovers, send one concise recovery block without solution, execution, consequence, mute, or threshold controls; retry recovery delivery only until Telegram confirms acceptance.
- Separate observation state from delivery state: record the sanitized current observation, but advance the notification's delivered fingerprint only after Telegram confirms `ok` with a `message_id`; on an uncertain or failed send, reconcile provider acceptance before retrying, because marking delivery before the external side effect can silently suppress the next alert while retrying blindly can duplicate it.
- In every operational message, convert raw quantities to human-readable units (for example, MiB/GiB/TiB, %, ms/s) and add a brief reason for each alarm or degraded resource. State the observed cause (such as restart count, readiness, CPU, memory, disk, latency, or availability); when Horus does not expose the cause, say that explicitly instead of guessing.
- Coalesce active alarms by the stable condition/resource identity and report only the highest active severity. If the same condition is already `critical`, do not add a preceding `degraded`/`warning` row just because that lower rule is also active.
- Every periodic or material-change status must contain a condensed macro view of Proxmox, TrueNAS, Docker, Kubernetes, and Uptime Kuma. Give one line per domain with only decision-relevant totals and health: Proxmox guests/resources/health, TrueNAS pool occupancy plus scrub and snapshot result, Docker container availability and host load, Kubernetes nodes/deployments/pods plus an aggregate restart warning, and Kuma monitor failures. Expand only material exceptions; explicitly state when per-resource health, uptime, restart cause, or individual snapshot inventory is not exposed.
- For each active or confirmed-persistent alarm or material diagnostic finding, present three separate fields: **solution** (what should fix it), **execution** (the concrete read-only checks and the approved change sequence), and **consequence if ignored** (the operational risk). Do not attach these fields to a recovered condition. Keep execution proposals bounded to the exact target and require permission before disruptive steps; never imply that a restart, cleanup, expansion, scrub, snapshot action, or threshold change was executed. Do not add a repetitive footer saying that no automatic action ran; absence of a mutation is already implicit unless an action result matters.
- Use OpenBao as the only Horus credential source. Resolve `infra/horus user` and `infra/horus password` with the profile-local `openbao-get` command and `OPENBAO_ENV=/home/kiwel/.config/openbao/tiberius.env`; keep both values in process memory only long enough for `POST /api/login`, then keep only the returned session token for the API calls. Validate `GET /api/me` as the normal user. Never place either secret or the session token in this skill, memory, chat, URLs, screenshots, command output, logs, or reusable files. Missing, ambiguous, malformed, or unavailable fields fail closed without prompting; ask the operator to create the missing OpenBao secret, never ask for its value in chat. Do not use `rbw`, Bitwarden, Hermes browser-vault login, or any fallback credential source.
- Start with read-only calls. A non-running status is evidence to investigate, not permission to restart, stop, delete, acknowledge, roll out, or change configuration.
- For a state-mapping task, close the loop by updating the canonical wiki page, `wiki/index.md`, `wiki/log.md`, and the environment-specific state/skill changelog; persist only sanitized, dated facts and remove raw captures.
- In multiplexed or external no-agent cron workers, do not assume profile-scoped environment hydration is present; resolve `infra/horus user` and `infra/horus password` directly through the OpenBao helper inside each short-lived monitor process. Pass only the OpenBao env-file path to each child, capture stdout/stderr, discard the login values after `/api/login`, and never inherit, log, persist, or print the credentials or session token.
- OpenBao lookup is non-interactive and does not depend on an unlocked local password manager. Never add a password-manager fallback or prompt to make a missing OpenBao path appear healthy.
- Ask for explicit permission before any action that can interrupt service, change data/configuration, alter monitoring state, or affect more than one target. The user's standing authorization covers non-disruptive changes inside Horus (dashboard layout, charts, gauges, and alarm rules) and manual Proxmox health diagnostics; it does not cover host/service control, credential changes, integration changes, or disruptive operations. State the exact target, expected impact, and rollback or recovery path.
- Verify external state after every approved action by reading the exact target back from Horus and, when relevant, the underlying service manager or platform. Do not treat a successful API response as proof that the requested state was reached.
- Separate expected stopped/ephemeral resources from incidents. Kubernetes job pods, old reindex pods, disabled monitors, intentionally powered-off VMs, and Proxmox guests with `attributes.template: true` require context before escalation; maintain the known template exception list and do not infer it from a name alone.
- Never treat zero active alarms as proof that every entity is healthy. Cross-check per-integration statuses and validate material deviations against the underlying platform—especially Kubernetes jobs/pods and Proxmox templates—before escalating or dismissing them.
- Report observed facts, uncertainty, and proposed next step separately. Do not turn aggregate counts into root-cause claims.

## Procedure

1. **Check scheduler state before reactivation.** Run `hermes -p <profile> cron list`, `hermes -p <profile> cron status`, and `hermes -p <profile> cron doctor`. Treat an `[active]` job and a healthy ticker as already running; do not resume or duplicate it. Separate scheduler state from collection/auth state: an active job can still fail closed when its Horus credential is unavailable. Reactivate only an explicitly paused job after checking its credential source and intended Telegram target.
2. **Establish Horus access.** Resolve `infra/horus user` and `infra/horus password` through `openbao-get` with `OPENBAO_ENV=/home/kiwel/.config/openbao/tiberius.env`; capture both results without printing them. If either field is missing, stop and ask the operator to create that OpenBao secret without requesting its value. Send them only to `POST /api/login`, retain the returned session token in memory, validate `GET /api/me` as the expected normal user, and stop on authentication or reachability failure without attempting control operations. Do not use a token-only path, `rbw`, or another credential source.
3. **Capture a read-only snapshot.** Fetch `/api/entities` and `/api/alarms/active` in addition to `/api/me`. Parse JSON programmatically and retain only the fields needed for triage: `id`, `integration`, `type`, `name`/`display_name`, `status`, `parent_id`, `last_seen`, and relevant attributes.
4. **Triage deviations.** Count statuses, then aggregate by domain/integration/type instead of dumping every healthy entity. Cross-check active alarms and freshness (`last_seen`). For Proxmox, inspect `attributes.template` and the diagnostic `excluded_guests` before escalating a stopped guest; a template is expected to be stopped, while a non-template with `onboot=1` is actionable. For Kubernetes, inspect ownership and pod/job age before calling a failed or stopped pod an outage; summarize repeated pod restarts as one material condition and name the cause only when observed. For Uptime Kuma, treat a monitor error as an indication that its target may be down, not proof of the target's cause.
5. **Drill down read-only.** For each material deviation, use the entity detail/latest/health/metrics/log endpoints documented in `references/horus-api.md`. For a Proxmox host, inspect `result.ran_at`, `result.overall`, `result.categories[*].findings`, `excluded_guests`, and `running`; if the result is stale or a finding needs validation, POST `/api/entities/{id}/health/run` and then GET `/health` again. Treat the diagnostic run as collection, not remediation, and preserve template exclusions and findings. Prefer the narrowest query that answers the question; avoid dumping the full entity inventory into a response.
6. **Choose a response.** If the condition is expected or transient, document it and continue monitoring. For every material alarm, write separate solution, execution, and consequence-if-ignored lines; make the execution sequence concrete enough to approve or reject. For dashboard, chart, gauge, and alarm-rule changes inside the standing Horus scope, audit current rules/history and apply the smallest non-disruptive change without requesting a second approval. For remediation outside that scope, present a concise Telegram decision with buttons for the recommended action, a safe alternative, and defer/no action. Include downtime and scope. Never bundle unrelated changes under one approval.
7. **Execute only the approved operation.** Use the Horus control endpoint or the platform's supported service mechanism, targeting the exact entity ID. Do not use bulk verbs or wildcard targets unless the user explicitly approved that scope.
8. **Verify and close.** Re-fetch the exact entity/task, active alarms, and relevant logs until the operation reaches a confirmed terminal state or the timeout is reached. Report the real result, residual warnings, and any follow-up; do not claim success from intent or an accepted task alone.

## Scheduled monitoring and Telegram delivery

- Register scheduled Horus jobs in the Hermes profile that owns the running gateway and Telegram bot. In multiplex mode, route an exact `telegram:<chat_id>` target to the secondary profile with the default gateway's `gateway.profile_routes`, validate that the primary runtime lists the profile in `served_profiles`, and do not mistake a satellite profile's standalone `cron status` for the multiplexer's liveness. Verify the primary `hermes cron status` has a live ticker and run `hermes cron doctor`; `deliver=telegram` without a resolved origin/home target is a delivery failure, not a successful notification.
- Before a Telegram profile cutover, validate each bot identity with `getMe` without displaying tokens, pause the old profile's monitoring jobs, restart the authorized gateway only after stating the brief impact, and verify both platform states. A private Telegram bot cannot initiate the user's DM: have the user send `/start`, then `/sethome`, before testing scheduled delivery. Keep the old jobs paused—not deleted—until the new bot has a confirmed `ok` delivery; resume them as the rollback path.
- Prefer no-agent scripts for frequent read-only checks: resolve `infra/horus user` and `infra/horus password` from OpenBao in process memory, authenticate through `/api/login`, keep only the short-lived session token needed for API calls, keep deduplication state as a hash plus the sanitized prior conditions needed to render a delta, require two consecutive five-minute observations before notifying new non-critical service/material conditions, and emit nothing when the material state is unchanged or a flap recovers before confirmation. Missing, malformed, or unavailable credentials must fail closed without an unlock prompt. For the three-times-daily cadence, use one **condensed macro** status script at explicit morning/afternoon/night times in `America/Sao_Paulo` (BRT, UTC−03:00); include action plans only for active/persistent material exceptions, keep recovery blocks factual and action-free, keep any high-frequency watchdog event-only and delta-only, and pause old summary jobs rather than deleting them until the replacement cadence and delivery are verified.
- Before enabling or modifying an event watchdog, test the renderer with a previous/current fixture: assert that a severity change produces one `🔄 alterado` item, an absent confirmed condition produces one concise `✅ resolvido` item with no solution/execution/consequence text or action controls, a condition that disappears before its confirmation window produces no delivery, an unchanged signature produces no delivery, and the output contains none of the periodic macro domain headers. Do not call the full `format_report()` path from an event-only watchdog, because deduplication can be correct while the notification still repeats the entire infrastructure report.
- Treat scheduled output as a user-facing Telegram report, not raw cron stdout. All Tiberius reports and alerts use the shared direct-delivery contract: compact thematic blocks, blank-line spacing, stable icon placement, no job metadata or stop-job footer, and `👍`/`👎` feedback buttons. Keep remediation/approval controls separate: feedback records presentation quality and never authorizes infrastructure changes; when remediation is needed, open an interactive decision flow with the smallest safe action, alternative, and defer/no action.
- Validate scheduler delivery without creating unwanted noise: inspect `cron list`, `cron status`, `cron doctor`, and the target job's last status/error before changing a renderer; test final rendered chunks locally with a dry run or mocked transport, measure UTF-16 length after HTML rendering, and assert every chunk is at or below 4,096 units. Never clear a historical failure or fire a production report solely to make the scheduler look green. After a fix, distinguish the old failure from new evidence and wait for the next scheduled run/readback before claiming delivery; require provider `ok` plus `message_id` for external acceptance. Keep the target identifier redacted in reports and never copy bot tokens between profiles. See `references/telegram-report-delivery.md` for the reusable recipe.
- When readable Telegram output is requested, configure the owning profile with `platforms.telegram.extra.rich_messages: true`, `rich_drafts: false`, `disable_link_previews: true`, and `display.platforms.telegram.cleanup_progress: true`; restart only after stating the brief gateway impact and receiving permission.
- If presentation needs an extra visual test message, request explicit permission first, send one bounded sample, and verify `success`, a `message_id`, the destination/profile, and the connected gateway state before reporting it. Do not resend after a timeout without a fresh decision.
- Horus Proxmox diagnostics store findings under `result.categories[*].findings`; parse those categories and preserve `excluded_guests` before reporting a clean or degraded result.

## Safe decision gates

| Operation | Permission required before execution |
|---|---|
| Read entity state, metrics, alarms, or logs | No, if the credential is already available and the request is within monitoring scope |
| Run a Proxmox/system diagnostic via Horus | Standing authorization within this homelab; verify `result.ran_at`, findings, and that no guest-control operation occurred |
| Restart, stop, start, delete, roll out, mute, acknowledge, or change thresholds | Yes; name the exact entity and expected impact |
| Change Horus dashboards, charts, gauges, or alarm rules | Standing authorization within this homelab; audit for duplicates/noise and verify the readback |
| Change Horus users, tokens, integrations, credentials, or backend configuration | Yes; treat as administrative change and verify the new configuration |
| Act on multiple entities | Yes; enumerate the scope and provide a rollback plan |

## Useful reporting shape

Use this order in Telegram, keeping the visual hierarchy compact and scannable:

1. **Resumo executivo:** alarm count and one thematic macro line for each of Proxmox, TrueNAS, Docker, Kubernetes, and Uptime Kuma.
2. **Alarmes:** only the highest active severity for each stable condition, with current value and observed reason.
3. **Plano:** for each material exception, show **solução**, **execução**, and **se ignorar**; aggregate repeated pods/containers/monitors instead of listing healthy inventory.
4. **Decisão:** buttons for the smallest safe next step, when action is needed, naming target, scope, downtime, and rollback.
5. **Após a ação:** exact verification result and remaining issues.
